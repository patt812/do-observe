# 追加質問への回答（3回目）

計測済み/未計測を明確に分けて回答します。

## Q0. Alarmの1秒周期は非推奨・最大1分遅延があり得る問題

ご指摘は正当で、当方も**alarm遅延とtick途絶の切り分けは世代IDと「同時性の形」で行っています**：

| 事象 | 見え方 |
|---|---|
| alarm遅延（ticker停止） | **全シャードの全接続が同時に**tickタイムアウト → 再接続すると**全DOで世代不変**（＝blipの全面波） |
| シャードDO死 | そのDOの接続だけ全滅 → **世代変化** |
| エッジ束切断 | 1DOの一部接続のみ → 世代不変 |

つまりalarm遅延は「全シャード同期のblip波・世代不変」という固有の署名になり、死とは混ざりません。実績としては約20時間の運用でこの署名の事象は**0回**でした（ちなみに当方のalarmは遅延どころか実装バグで約1.4回/秒と過走しており、それでも安定していました）。

とはいえ観測の穴（tick停止中は死活が見えない）にはなるので、本番でsetIntervalを選ぶ判断は合理的だと思います。当方がRPC駆動にしたのは、本番の「集計DO→シャードRPC」のバックプレッシャー構造を再現するためで、alarmはそのベンチ用の駆動源にすぎません。本番ではコメント到着という外部イベントが駆動源になるはずで、alarm問題自体が消えるはずです。

## Q1. yieldなしでどう壊れたか・500件の根拠

正直な申告：**yield単独のA/Bは取れていません**。「自走setInterval＋yieldなし」→「RPC駆動＋500件yield」へ2変数を同時に変えたため、厳密な寄与分離は未実施です。

- 壊れ方（変更前）: `Durable Object is overloaded. Requests queued for too long.` によるDO強制リセット。約5〜6分周期で無限ループ
- 500の根拠: アドホックです。5000本で9回yield＝受信イベントの最大待ちをブロードキャスト時間の約1/10（当方条件で〜30ms）に抑える意図。閾値スイープはしていません
- そちらの「430msで5000本・yieldなしで問題なし」は当方の理解と矛盾しません。当方も自走モデルで**定常時は1.9時間無事故**でした。壊れるのはブロードキャストと**churn（大量close/upgrade）が重なった瞬間**で、閾値は「1回の送出時間」ではなく「受信キューの滞留時間×継続」にあります。RPCペーシングが効いているならyieldは保険程度、ただし再接続ストーム時の生存性を上げる安価な保険です

## Q2. リセットループの誘発条件・ペイロードと帯域

- ペイロード: **約150B**、当時1msg/s → 5000本で**約0.75〜1MB/s**。そちらの63MB/sよりはるかに小さく、**帯域・ペイロードは無関係**でした
- 誘発条件（再現手順として書けるレベルで）:
  1. 自走setInterval（バックログを無視して毎秒発火）
  2. そこに**1000本の同時close**が着弾（観測クライアント1台の停止が起点）
  3. close処理＋timer発火が滞留 → 過負荷リセット
  4. リセットで5000本切断 → **ジッターなしで約2秒に5000本のupgradeが再着弾** → 3に戻る（自己持続）
- つまり「unpacedな送出 × churnの重なり」が条件で、送出帯域の限界ではありません。限界帯域は当方も未計測です

## Q3. エッジdrain束切断の頻度（5000本シャード実測・約9時間）

- **平常時間帯**: 束événement（≧5本同時）はほぼゼロ。単発切断が毎時1〜5本
- **波の時間帯（JST深夜〜明朝＝米国昼）**: 束切断が**毎時1〜3回**、1回あたり**10〜110本**。最悪の1時間でシャードの約2%が切れた計算
- 束の内部は約2秒以内に収まり、復帰は全件1.6秒以内（即時再接続時）

## Q4. 無言死の検知遅れ

- 当方のタイムアウトは3.5秒（tick 1秒＋マージン）なので**無言死でも最大3.5秒**
- ただし重要な実測として、**観測できたDO死はすべて「無言」ではなくEOFでした**（killテストは5000本全部EOF、自然死候補も検知〜復旧1.5〜2.1秒でタイムアウト待ちの形跡なし）。TCPが即座に終端されるため、検知遅れが問題になるのは経路が黙って死ぬケース（エッジ側ストール等）に限られます
- 検知遅れのスケーリングは単純に「配信間隔＋マージン」です。60秒pingなら最悪60秒盲目、はその通り
- ひとつ指摘を：そちらは**配信中は30msg/sのデータストリーム自体がtickの役割を果たす**ので、実効の検知遅れはサブ秒のはずです。60秒盲目が効くのは**アイドルシャードだけ**で、そこはHibernation節約との純粋なトレードオフになります（配信外のシャードの死を60秒以内に知る必要があるか、で決める話）

## Q5. 遅い接続の送信バッファ上限

**未計測です。** 当方のクライアントは常に即時読み取りするため、滞留を一度も発生させていません。分かっているのは (a) send()は非ブロッキングで背圧APIなし、(b) 滞留はDOメモリに乗る、(c) 当方の運用でメモリ系エラーは一度も出ていない、まで。上限値と溢れ時挙動（ソケット切断かDOリセットか）は、クライアント側を tc で帯域制限（例:128kbps）すれば安全に測れるはずですが、未実施です。

## Q6. Ticker DOの受信上限

**未計測です。** 当方のTickerはalarm駆動で受信がほぼゼロのため、そちらのpublisher DO（受信700/s）に相当する負荷がかかっていません。関連する間接データとして、シャードDO側は再接続ストーム時に数秒間で5000本のupgrade（瞬間数千/s着弾、うち約4割を接続確立エラーとして弾きつつ）を捌いています——持続RPSのベンチではないので参考値です。「受信と配布の取り合い」という見立ては当方のQ1/Q2の機構理解（シングルスレッドのキュー滞留）と整合するので、配布側にyieldを入れる or 配布を別DOに分離すると受信上限が上がる方向の予想です。分離計測するなら「配布を止めた状態の受信RPS」を先に取るのが早いと思います。
