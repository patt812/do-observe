# 追加質問への回答（2回目）

前提の訂正を1つ：観測は**まだ約2日**です（2〜4週間の値はこれから貯まる）。以下は現時点の実測で、n が小さい箇所は明記します。

課金の向きのご指摘はその通りです。**incomingは課金（20:1）、outgoingは無料**なので、キープアライブをサーバー→クライアントのtickで駆動すると観測コストがほぼゼロになります。client→DOのping駆動とは費用構造が逆になります。

## Q1. 実測値（約2日・国内VPS観測）

**死亡頻度（CF都合の候補）**
- 無負荷コホート（1本接続×6 DO）: **1晩目に6件**（6台中4台、s-0×2/s-1/s-3/s-4×2、直前稼働2.5〜5.1h）。**2晩目はゼロ**
- 負荷ありコホート（100本×4、1000本、5000本）: **2日間でゼロ**（延べ約20 DO日）
- 粗い言い方をすると「アイドルDOはバースト日に〜1回/DO/日、活動中DOは観測範囲でゼロ」。「アクティブなDOほど殺されにくい」仮説はn不足で未確定

**downtime分布**
- クリーン計測できた死（再接続を即時にしていた期間）: **1.5s / 2.1s**（切断検知→新世代で受信再開）
- 制御kill: 100本DOで**1.17s**、5000本DOで**初着2.4s**
- バースト夜の6件は当時クライアント側に0〜60秒の再接続分散を入れていたため18〜73sと記録されているが、これは自衛ジッターの値段であり素の復旧は数秒と推定
- 参考: blip（DO生存の個別切断）の復帰は395件全件 **0.19〜1.61s**

**時間帯の偏り**
- 死亡6件は **04:05〜06:55 JST** に集中。個別切断のバースト（後述）も2晩とも **おおむね03:45〜08:00 JST**（米国太平洋の昼前後）に出現。日中JSTはどちらもほぼ皆無

**colo変化**
- 確認できた範囲では **同一colo内での再作成**（例: KIX→KIX）。ホスト移行らしき colo 跨ぎは未観測。ただし新世代のcolo自己申告が非同期解決のため記録時点で空のケースがあり、断定にはデータ追加が必要

**同時性の相関**
- **DO死同士の相関はなし**（6件は2時間50分に分散、別DO）
- 一方 **WS切断は束で相関**する: 同一DOの接続のうち10〜110本が約2秒以内に同時に切れる事象が日常的にある（エッジマシン単位のdrainと解釈。世代不変なのでDO死ではない）

## Q2. 「5000本一斉再接続で死に続ける」の顛末

時系列で全部書きます。

1. **初期実装（DO内setInterval自走 + ジッターなし）**: 5000本DOが「過負荷リセット→約2秒で5000本再接続→約5〜6分後にまたリセット」の**自己持続ループ**に入った。放置したところ**一晩で80サイクル以上、十数時間継続**（自然停止しない）。各サイクルのuptime中央値6.6分、downtime 1.6〜2.5s。Workers Logsに `Durable Object is overloaded. Requests queued for too long.` が毎サイクル記録される
2. **Prober側ジッター（0〜60s一様分散）を導入**: uptimeが一度22分まで伸びたがループは再発。**クライアント側ジッターだけでは不十分**だった
3. **負荷モデルをRPC駆動（Ticker DO）+ チャンク配信に変更**: ループ完全消滅。**20時間以上安定**
4. **その後ジッターをほぼ撤去（0.1〜1sのみ）して制御kill**: 5000本が即時一斉再接続しても再死せず。初着2.4s、dial試行は平均1.6回/接続（超過upgradeは接続確立エラーとして弾かれ、指数バックオフで数秒内に全収容）

結論: 死のループの主因は再接続ストームではなく **自走ブロードキャストがイベントループを譲らないこと**。外部ペーシング＋yieldがあれば、5000本の同時再接続はランタイムの自然シェディング（弾く→リトライ）だけで収束し、クライアントジッターは実質不要だった。READMEの記述はこの経緯の初期段階を指しています。

## Q3. server.accept() で5000本保持したときの実挙動

**メモリ**: isolate内から実測するAPIがないため直接値は不明。間接証拠として、150B/秒×5000本の定常運転20時間超で `exceededMemory` 系のエラーは一度も出ていない。過負荷リセットの原因はメモリではなく**リクエストキュー滞留**（ログの文言どおり）だった。

**duration課金**: 接続数に**完全に無関係**。「メモリ常駐wall-clock × 128MB」で、5000本でも1本でも常駐DOは約$4.15/月。

**ブロードキャスト所要時間**: Ticker DOのRPCラウンド計測で、11シャード（うち1つが5000本fanout）の1ラウンド **約200〜330ms**。支配項は5000本チャンク配信で、150Bペイロードなら5000 send ≈ 200〜300ms（yield 9回込み）。ペイロードが数KBになれば線形に伸びる想定。

**500件ごとにawaitを挟む理由**: DOはシングルスレッドで、同期5000連続sendはイベントループを丸ごと占有する。その間に届く受信イベント（新規upgrade・close・次のRPC）がキューで待たされ、滞留がworkerdの過負荷閾値を超えると**DOごと強制リセット**される。500件ごとに `await new Promise(r => setTimeout(r, 0))` で制御を返すと合間に受信イベントが捌け、これの有無が「5〜6分ごとに死ぬ」と「20時間無事故」の差だった。あわせてTicker側が**前ラウンド完了まで次を送らない**ため、シャードが遅い時はtickが落ちる（スキップ）方向に壊れ、キューが積み上がらない。
