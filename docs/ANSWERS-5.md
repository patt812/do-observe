# 追加質問への回答（5回目・メンテバッチの同時巻き込み台数）

## 結論から

**「同時に落ちる」は観測されていません。1晩目の6件（4台）は同時ではなく、約3時間にわたるローリングでした。**

死亡イベントの実タイムスタンプ（8/2 早朝JST）:

```
04:05  s-4
04:26  s-1   (+21分)
05:31  s-4   (+65分)
06:12  s-3   (+41分)
06:43  s-0   (+31分)
06:55  s-0   (+12分)
```

- 隣接イベントの最短間隔でも**12分**。秒〜分オーダーで複数DOが束で死んだ事例は**ゼロ**です
- つまり現時点の実測では「同時死亡台数の分布」は**全事象でサイズ1**。CFのメンテはDOに対しては（少なくともこの夜は）1台ずつローリングで当ててきた、という見え方です

## 紛らわしい対比: WSの束切断はDOをまたいで「同時」

エッジマシンのdrainによる**接続の束切断**は、同一秒に複数DOへまたがります（例: 同じ2秒間にl-0の数十本＋m-0＋m-1が同時切断。同じエッジ機に載っていた接続が一括で切れるため）。ただしこの場合**DOは全台生存**（世代不変）です。

- **接続レイヤ**: 同時・複数DO横断で切れる（フォールバック不要、即時再接続で1〜2秒）
- **DOレイヤ**: ローリングで1台ずつ（観測範囲）

## フォールバック設計への示唆と留保

- 観測ベースでは「**同時に失うシャードは1つ**」を前提にでき、N+1的な余裕（隣接シャードへの一時退避 or 再接続待ち2〜3秒）で足ります
- **重要な留保**: n=1晩・アイドル6台での観測です。当方のフリートは計11台なので、そもそも観測できる同時数の上限が小さい。また、colo障害級のインシデント（リージョン単位で複数DOが同時消失するケース）は今回の観測期間には含まれておらず、この分布では捉えられません。フォールバックの最終防衛線はこの「相関災害」を別枠で想定しておくのが安全です

## 今後の集計方法（実装済みのデータで可能）

死亡イベントはすべてタイムスタンプ付きでJSONLにあるため、「60秒以内に発生した死亡を同一バッチとみなす」窓でバッチサイズ分布を機械集計できます。観測期間の延長に伴い、この分布（現状は全部サイズ1）を定期スナップショットに含めます。
