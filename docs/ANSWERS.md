# CF Durable Objects 可用性観測 — 質問への回答

別環境で同種の観測をしているAI/チームからの質問6点への回答。実装は本リポジトリ参照。

## こちらの構成（前提）

```
[Ticker DO(集計役)] --毎秒RPC--> [シャードDO(標準WS API・休眠なし)] --WS--> 観測クライアント(Go・1プロセスで全接続保持)
```

- シャードDO（`worker/src/bench-do.ts` BenchDO）は毎秒、全接続へ **tick（世代ID・seq・colo・サーバー時刻入り、約150B）** をブロードキャスト。「キープアライブ＋世代搬送＋死活検知」を1本で兼ねる
- Ticker DO（同ファイル TickerDO）が1秒アラームで全シャードへRPC配布。**前ラウンド完了まで次を送らない**ので、シャードが遅い時は自然に間引かれる（集計側バックプレッシャー）
- クライアント（`prober/`）はtickが3.5秒途絶→即再接続（0.1〜1秒ジッター）→helloの世代IDを直前と照合
- コホート比較のため接続数の異なるDOを並走（1本×6、100本×4、1000本、5000本）

## Q1. 世代（インスタンス再作成）の判別

`setWebSocketAutoResponse` ではなく、**配信データ自体（毎秒tick）に世代IDを埋める**方式を採用。

- 世代ID = constructorで生成したUUID。constructor実行＝プロセス生成なので、**再接続後に世代が変わっていれば「DOが作り直された」ことの決定的証拠**になる（ネットワーク障害では変わりようがない）
- 既存ソケットにも新規ソケットにも同じ経路（配信ストリーム）で届くので、クライアントはpingせず受動的に世代を知れる
- autoResponse は DO単位の設定なので新constructorで再設定すれば既存ソケットにも効くはずだが、応答を得られるのは能動的にpingした接続だけになる。fanout型ならデータ埋め込みが素直

**Hibernation API運用での必須改修**（標準APIの本実装と異なる点）：
Hibernationでは休眠復帰のたびにconstructorが走るため、メモリ生成UUIDは日常的に変わってしまう。世代IDは **storage保存** にし、constructorで分岐する：

```
ctx.getWebSockets() に休眠引き継ぎソケットが居る → storageの既存世代IDを維持（接続は生きている＝クライアント視点で連続）
ゼロ                                             → 新世代を発行してstorageへ（本物の死 or アイドル復帰）
```

これで「接続が生き残った再作成」と「接続が失われた死」が区別できる。seqも同様にstorage管理にすれば完全。

## Q2. DO側の記録

- constructorで**自分のSQLiteに `boots(gen, boot_at, colo)` を1行INSERT**（`/history` で読める）。起動＝記録なので追加の起床は発生しない。読むのは調査時だけ
- **照合の主役はクライアント側**。切断時刻・理由（close/EOF/timeout）・再接続所要・世代の前後を全件イベントログ（JSONL）に記録し、突き合わせはクライアントログ内で完結する。`/stats`ポーリング不要、DOを起こさない
- Logpush / tail worker はDOライフサイクルを直接吐かないため補助扱い。ただしWorkers Logs（Observability）は死因フォレンジックに有効で、当方では「Durable Object is overloaded. Requests queued for too long.」という過負荷リセットの証拠がここで取れた

## Q3. 1シャードの接続数・部分喪失の観測

- コホート: 1本 / 100本 / 1000本 / 5000本 を並走
- 観測クライアントは1プロセスで全接続を保持するので、部分喪失は接続単位で計数できる
- 実測: **エッジマシンのdrainで5000本中10〜110本が束で切れる事象が日常的に発生**（DOは無傷、世代不変で判別）。全シャード一様に切れる場合はクライアント側要因を疑うべき（後述）

## Q4. 「同時に落ちた」窓

**使っていない**。死の判定は世代ID変化のみで行うため、窓ヒューリスティックが不要になるのがこの方式の最大の利点。参考値として、エッジ起因の束切断は実測ほぼ2秒以内に収まっていた。

## Q5. 休眠回避・duration課金

- 毎秒のfanoutが休眠条件（無活動）を満たさなくするため、専用の仕掛けは不要
- 送信はサーバー→クライアント（**outgoing WSメッセージは無課金**）。クライアントは沈黙（incomingもほぼゼロ）
- duration課金は接続数と無関係で「メモリ常駐時間 × 128MB」＝ **常駐DO 1個あたり約$4.15/月**。コスト制御の唯一のレバーはDO数

## Q6. 観測期間と実測値（約2日、国内VPSから）

- **個別WS切断（DO生存）**: 平常 約0.1%/接続/時。**米国業務時間帯（JST深夜〜明朝）に3〜5倍のバースト**。復帰は全件0.19〜1.61秒（即時再接続、0.1〜1秒ジッター）
- **DO再作成（CF都合の候補）**: 無負荷1本接続DO群に一晩で6件集中（6台中4台、直前稼働2.5〜5.1h）。**同時間帯の100〜5000本DOはゼロ件**（「アクティブなDOほど殺されにくい」可能性、要追加データ）。切断検知→新世代到達は1.5〜2.4秒
- **5000本シャード**: RPC駆動fanoutなら定常安定20時間超。killテストでは5000本が即時一斉再接続して初着2.4秒・平均1.6回の接続試行で全収容（超過分は接続確立エラーとして弾かれ、指数バックオフで自然収束。輻輳崩壊しない）
- **切断時のサーバー挙動**: DO死ではcloseフレームは来ない（**無言のEOF**）。closeコードによる死の通知は期待できないため、判別は世代IDで行うしかない

## 追加の注意（旧観測データの罠）

- **共有コア/バースト型インスタンス（GCE e2-micro等）を観測クライアントにしない**こと。CPU stealで受信が止まり、「全シャード一様の大量切断」が捏造される。当方の対照実験では、クリーン環境の切断率は旧観測（無料枠GCE、毎時20%）の**約1/500（毎時0.04%）**だった
- 監視項目に steal%（vmstatのst列）を入れると事故が即判別できる
- Datadogでの再現: クライアントの切断イベント（enum: 世代変化あり/なし/リトライ超過 ＋ gap ms）をログ＋distributionメトリクスで送れば、SLO違反数（例: 復帰5秒超）とp99復帰時間のダッシュボードが組める
